## 一、把「官方原文」和「我们的推论」分开

| 说法 | 性质 | 依据 |
|---|---|---|
| 该项 10 分，考察「训练日志、调优过程、平台使用规范」 | ✅ **官方原文** | 官方评分细则（`docs/roles/README.md:24-25` 逐字引用） |
| 「平台」指的是咪咕仝学 | ❓ **推论** | 原文未点名。可能指赛方提供的平台，也可能泛指我们使用的所有算力平台 |
| 必须开带 GPU 的实例跑一次 | ❌ **无依据** | 原文没有任何关于卡型、时长、是否带 GPU 的要求 |
| 跑得越久分越高 | ❌ **无依据** | 原文看的是「日志 / 过程 / 规范」，不是卡时消耗量 |

**结论：这 10 分要的是「能被读懂的运行证据」，不是「烧了多少卡时」。**

换个角度想：如果评审真的要 GPU 运行时长，那拿着无卡券的队伍就天然拿不到这 10 分——
这个评分项就变成了「你有没有钱」，而不是「你做得规不规范」。这不合理。

## 二、无卡模式（CPU 实例）够不够？

**大概率够，而且我们有真实的 CPU 活儿可以跑。** 理由：

1. 评审要看的是「训练日志、调优过程、平台使用规范」这三样**文档性证据**，
   没有任何一条要求「必须在 GPU 上产生」。
2. 无卡模式实例仍然是**平台的使用**——创建、配环境、跑任务、关机，这整套
   动作本身就是「平台使用规范」的可观察对象。
3. **我们确实有 CPU 就能跑完的真实工作**，见下表。这些不是凑数，
   是本来就要跑、而且现在就能在平台上跑出日志的东西。

| 能跑在 CPU 上的真实工作 | 命令 | 产出 |
|---|---|---|
| 构建检索语料 | `python rag/corpus/build_corpus.py` | `corpus.jsonl`（18,657 条 / 17.7 MB） |
| 构建 BM25 索引 | `python -c "from rag import retrieve; retrieve.warm_up()"` | `bm25.pkl`（11.7 MB），实测 0.19 s 加载 93,311 个 term |
| 本地评测打分 | `python src/cli.py eval --predictions X.jsonl` | BLEU-4 / ROUGE-L / 情绪 Acc / 画像 Acc |
| 提交格式校验 | `python src/cli.py validate --submission X.jsonl` | schema 合规性 |
| 单元测试 | `python -m unittest discover -s tests` | 26 条回归 |

**「调优过程」怎么来**：上面每一项都带一个可比较的数字（语料条数、索引 term 数、
某个版本的 BLEU-4）。把这些数字按时间顺序排起来，就是一条真实的调优链。
这比「我开了一张 4090 跑了一小时」有内容得多。

## 四、不确定时期的做法：两处都记，成本为零

既然不知道「平台」指谁，就不要赌。**哪台机器跑的都记一份**，最后按需裁剪。

```
docs/platform-log/
├── README.md                 ← 本文件
├── session-template.md       ← 单次记录模板
├── preflight-checklist.md    ← 镜像提交前的自检清单
├── migu/                     ← 咪咕仝学平台（无卡/有卡都记这里）
│   └── YYYY-MM-DD-<主题>/
└── modelscope-amd/           ← 魔搭 AMD MI300X 开发机
    └── YYYY-MM-DD-<主题>/
```

**为什么要两个都记**：
- 如果「平台」＝咪咕 → `migu/` 目录直接就是答案。
- 如果「平台」泛指 → 两个目录合起来才是完整的「调优过程」，而且 AMD 上的
  SFT 训练日志（loss 2.33 → 1.29，2282 步）本来就是最有说服力的一份「训练日志」。
- 记一次的成本是几分钟；漏记的成本是 10 分。

**唯一不能做的是伪造。** 日志、截图、指标一律要真跑出来的；跑不出来就写「未跑」。

## 五、每次运行的标准动作

### 跑之前

1. 明确**这一次只回答一个问题**，写进模板的「本次目标」。
2. 代码推到 GitHub，记下 `git rev-parse HEAD`。
3. 估一下耗时，别把券烧在装环境上——环境装好一次就存快照/复用。

### 跑的时候

4. **截图 1：实例创建页**（卡型/规格、镜像、创建时间）。无卡模式也要截，它证明「规范使用」。
5. 克隆代码 → 记录 commit。
6. 全程 `tee` 到日志：
   ```bash
   python your_cmd.py 2>&1 | tee runs/$(date +%Y%m%d-%H%M)-session.log
   ```
7. **截图 2：终端跑起来那一刻**（有命令、有时间、有进度）。
8. **截图 3：跑完的结果**（指标 / 产物路径）。

### 跑完

9. **立刻关机**。空占实例是「平台使用规范」唯一明确的扣分点。
10. **截图 4：关机确认页**。
11. 日志拖回本地，放进对应目录。
12. 复制 `session-template.md` 填好，提交。

## 六、自检：这次算不算「留下了记录」

跑完对 6 条打勾，**有一条空着就等于白跑**：

- [ ] 有带**时间戳**的终端日志，能看出开始与结束
- [ ] 有**代码版本**（commit hash），能对上仓库里那一版
- [ ] 有**这次要回答的问题**（不是「跑了一下」）
- [ ] 有**结果数字**，且注明了样本量 n
- [ ] 有**资源消耗**（卡时/AIQ，无卡模式就写 CPU 时长）
- [ ] 有**关机**的证据
