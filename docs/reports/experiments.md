| 项 | 口径 | 出处 |

### ⚠️ 三个会读错数的地方

1. **部分样本实验（`--limit N`）的真值会自动收窄到同一批 id**（`8a61e72` 之后）。
   在此之前，缺预测的样本按 0 分计入，`--limit 5` 会跑出「情绪 Acc 0.0013」——
   那不是模型崩了，而是 `0.6 × 5/2354` 的稀释结果。现在 `--limit` / `--offset` 会把真值同步切到
   同一批 id（写进 `runs/eval-<tag>/val_references_subset.jsonl`），冒烟数字直接可比：
   同一份冒烟产物，修前 0.0013 → 修后 **0.6000**（`runs/leaderboard.tsv` 的
   `smoke` 与 `smoke-rescore` 两行）。**全量跑仍用完整真值**，不受影响。
2. **本地评测器不是官方评分器**。官方未公布各指标权重与延迟满分阈值，
   本文件的数字只能用于「同一份数据、同一套代码下 A 方案是否比 B 方案好」的判断。
3. **E0 / E1 量的是哪一棵树**（2026-10-16 补记，`9b54fae`）。
   `tools/eval_loop.py` 在 `9b54fae` 之前的默认推理脚本是 `GivenData/participant/run_inference.py`
   —— 那是**官方原件，没有接线层**，读不到队友的 `prompts/` 与 `rag/`。所以 E0 与 E1 量到的都是
   「官方提示词 + 3B 模型」，**不是**我们要提交的那棵树。主办方唯一执行的命令是
   `bash /root/participant/start.sh TEST_FILE RESULT_DIR`（`GivenData/participant/README.md:80-86`），
   跑的是容器里那份，即 `deploy/participant/`。

   这对 E0 / E1 本身不算错——我们本来就需要一条裸基线——**错的是台账上看不出这件事**：
   一行数字分不出「官方裸基线」还是「带队友提示词与 RAG 的那棵树」。`9b54fae` 的修法是：

   - `--inference-script {wired|official|<路径>}`，默认 `wired`；要裸基线就显式写 `official`
   - 台账加 `script` / `prompts` 两列，行里自带「量的是哪棵树」
   - 开跑前先问接线层自己「这一趟走了哪条路」，把答案写进日志（`probe_wiring()`）

   **这两个新列的覆盖范围要说清楚**，否则会以为台账已经能自证：只有**真的跑了推理**的行才有值；
   `--skip-inference` 重新打分的行写 `(skip)`（那种行的产物来自一个文件，工具无法替它声明出处）；
   列头迁移时，`9b54fae` 之前的旧行一律补 `n/a`。所以 **E0 / E1 那两行的出处只能看本文档**，
   不能只看台账。另：`runs/` 被 `.gitignore` 覆盖，台账与各次产物**都不进仓库**——
   这份文档是它们唯一的对外载体，所以本节每个数字都写了产物路径。

   两个连带的坑一并处理了：`deploy/participant/model/` 不存在（5.9 GB 不复制第二份），而两份
   `inference_config.json` 都写 `"./model"` 且以**工具目录**为基准 —— 换脚本而不同时指定模型，
   模型就会找不到；`deploy/participant/prompts/` 本地同样不存在（镜像里由 `deploy/build.sh` 现拷），
   不显式指回仓库根的 `prompts/` 就会**静默**退化成官方提示词，量到的数不对应提交的那棵树。

#### E1 真正的结论：裸模型输给两条最笨的常量策略

这不是修辞，是算出来的：

| 策略 | 情绪 Acc | 画像 Acc（三维均值） |

> **2026-10-17 更正（重要）**：本表上一版把「画像一律留空」写成能拿 **0.6283**，

> 两个口径并修掉 `set() == set()`（commit `53ca3eb`），`src/cli.py` 会打印「官方口径」那一行。

复算命令（真值只有 val 一份，任何人都能跑出同样的数）：

```bash
.venv/Scripts/python.exe -c "

r=[json.loads(l) for l in pathlib.Path('data/processed/val_references.jsonl').read_text(encoding='utf-8').splitlines() if l.strip()]
n=len(r)
print('多数类', collections.Counter(x['target']['emotion_label'] for x in r).most_common(1)[0], n)
[print(d, sum(1 for x in r if not x['target']['user_profile'].get(d)), n) for d in ('personality_traits','interests','style')]
"
# 情绪多数类 anxiety 751/2354 = 0.3190 →「一律答 anxiety」就是这个分
# 逐维留空 1456 / 1763 / 1218 —— 旧口径下均值 0.6283，官方口径下 **0.0000**（空值判错）
```

**为什么这条比 E1 那个分数本身更要紧**：裸基线的情绪指标**还没有超过零成本的下限**。
而画像这一项没有「留空蒙对」这条路——真值里 37.17% 样本三维全空，可预测侧一旦跟着留空，
官方口径直接判 0。所以画像不是「守住下限」的问题，是**能不能产生任何非空命中**的问题：

| | 三维全空占比 |
|---|---|
| 真值侧 | 875 / 2354 = **37.17%** |
| 裸模型预测侧 | 1,868 / 2354 = **79.35%** |

模型留空的倾向是真值的 **2.1 倍**。角色②的提示词要打的第一个靶子是「别少写」，
而不是「写得漂亮」。

#### 四条必须一起读的限定

1. **这不是官方分数。** 官方未公布指标权重与延迟满分阈值；本行只能在「同一份数据、同一套代码」
   下做 A/B 对照。
2. **延迟不可跨机器比。** 本机是 RTX 5070 Laptop（12 GB, sm_120），官方性能分在 4090 上计。
   这里的 2,590 ms 只作**本机改进前后**的对照。
3. **micro-F1 低而 Acc 不低，是「集合精确匹配」口径的必然结果**：多写一个错标签该维直接归零。
   三维 micro-F1（0.0096 / 0.0612 / 0.0186）远低于 Acc，不要用 F1 判断好坏。
4. **BLEU-4 0.0116 不能用来判断回复质量。** char 分词只量字面重合，而情感陪伴的回复本就多样；
   这条数字只能作「同一提示词改版前后」的相对对照。

**这几条指标到此成为全队改进的对照底。** 后续台账里任何带 `script=wired` 的行，
都是在跟这一行比。

### E3 画像：官方口径下的真实水位（这是本项目最容易被误读的一节）

官方规则（`GivenData/participant/README.md:100-102`）：「画像子项和记忆引用写为空数组……
**空值作为该项预测失败参与评分，不会获得该项命中分。**」
⇒ **留空 = 0 分**，不是「保守」，也不是「下限」。

验证集真值分布（n=2354，逐维）：

| 维度 | 空数组 | 非空 | 非空里是单标签 | 非空里最多的标签 |
|---|---|---|---|---|
| personality_traits | 61.9% | 38.1% | 73.2% | `sensitive` 42.6% |
| interests | 74.9% | 25.1% | 91.9% | `career_development` 19.9% |
| style | 51.7% | 48.3% | 83.0% | `rational` 43.9% |

三条参照线（官方口径，三维平均 Acc）：

| 策略 | 全量 2354 | 同批 300 条 |
|---|---|---|
| 三维全空 `[]` | **0.0000** | 0.0000 |
| 一律填先验标签（sensitive / career_development / rational） | **0.1209** | 0.1233 |
| 模型自选 + 空维兜底（旧提交策略） | — | 0.1189 |
| 模型自选、完全不兜底 | **0.0044** | 0.0044 |
| 完美预测（各维非空金标全中） | **0.3717** | — |

**结论**：「一律填先验标签」是这条赛道上一个非常硬的参照——它比模型自己填得还准。

2026-10-17 的四臂对照把这件事量清楚了。同一批 300 条、同一次推理，只改画像输出策略：

| 臂 | 不兜底 | 只补空（floor） | 一律常量（force） |
|---|---|---|---|
| A（旧画像提示词 × v8 回复） | 0.0044 | 0.1189 | **0.1233** |
| B（旧画像提示词 × v9s5 回复） | 0.0567 | 0.0889 | **0.1233** |

把 B 的三维拆开看，模型给出的非空标签命中率是 0.0667 / 0.0467 / 0.1533，
而同一批数据上常量是 0.1333 / 0.0300 / 0.2067 —— **两维输、一维小赢**。
也就是说：模型在画像这一项上确实有信号，但信号的净效果低于拿一个先验常量去撞。
A 臂之所以 floor 与 force 只差 0.0044，是因为它 92% 的维度本来就是空的，
floor 已经把结果推到了常量附近。

**做法与边界**：`deploy/participant/run_inference.py` 提供三种策略，
由 `PARTICIPANT_PROFILE_MODE` 选择（`floor` 只补空 / `force` 一律常量 / `off` 不动）。
默认仍是 `floor`，因为 `force` 的收益完全来自「验证集标签分布」，隐藏测试集分布一变就有风险；
但三档都能在镜像里用环境变量切换，且 `tools/apply_profile_floor.py --mode force`
可以对已有提交事后补算，不需要重跑推理。

**为什么这条不是「刷分」**：官方口径下留空必然 0 分，所以任何提交都必须填点什么；
问题只是「填模型的判断」还是「填先验」。我们用同一批数据把两者都测了，选了实测更高的那个，
并且把两种结果都写在这里。


### E4 回应质量（角色③，v8 提示词，n=2354）

| 指标 | 值 | 参照 |
|---|---|---|
| BLEU-4（char 分词） | **0.0332** | 门限 0.15（未达） |
| ROUGE-L | **0.1352** | 门限 0.15（差 0.0148） |
| 空回复率 | **1.10%** | 目标 0 |
| BERTScore | **未计算** | 本地无编码器，`score.json` 里 `computed=false` |

**长度杠杆的算术与它的失效**：BLEU-4 的 brevity penalty 是纯乘因子。参考总 token 310,061，
当前输出 221,476 → BP = 0.6703；输出总量只要到 310,061 就能让 BP = 1.0，理论上 BLEU-4
能乘 1.49 倍到 0.0481。**但这条算术只算了 BP，没算 4-gram 精度必须与参考对得上。**
实测（见 E5）强制加长后 4-gram 精度掉得比 BP 涨得更快，净效果是负的。**该杠杆作废。**

### E5 负结果：`min_new_tokens` 强制加长（n=20，本地 RTX 5070 Laptop）

| 臂 | BLEU-4 | ROUGE-L | 情绪 Acc | 耗时 | 中位字数 |
|---|---|---|---|---|---|
| 默认 | 0.0220 | 0.1306 | 0.3500 | 2.0 min | 90 |
| `min_new_tokens=200` | 0.0268 | 0.1182 | 0.2000 | 6.0 min | 86 |

**机制坑（值得记下来）**：`transformers` 5.19.0 已把 `min_new_tokens` 从
`GenerationMixin.generate` 的签名里删掉，作为未知 kwargs **静默丢弃**；但 `GenerationConfig`
里还留着这个字段。正确做法是构造 `generation_config` 传进去（已实现，`run_inference.py`）。

**为什么修好了还是没用**：模型输出的是 **JSON**，强制续写多出来的 token 落在 JSON 之外，
`parse_prediction` 只取第一个 JSON object，**多写的全被丢弃**。20 条里只有 7 条变长，
中位字数从 90 降到 86（没动）。

⇒ 环境变量默认 0（关），代码保留并把这条写进注释。

### E6 负结果：RAG 检索的 A/B（n=200，同批样本）

| 臂 | BLEU-4 | ROUGE-L | 情绪 Acc | 空回复 | 耗时 |
|---|---|---|---|---|---|
| A 无检索 `PARTICIPANT_MAX_RETRIEVED=0` | 0.0200 | **0.1182** | **0.3100**（62/200） | 4 | 15.6 min |
| B 带检索（k=3） | **0.0208** | 0.1151 | 0.2550（51/200） | 2 | 17.3 min |
| 差 | +0.0008 | −0.0031 | **−0.0550** | −2 | +1.7 min |

配对 McNemar：A 对 B 错 = 22，B 对 A 错 = 11，χ² = 3.030，**p = 0.0817**（0.05 不显著，
但方向明确偏差）。回复长度 A 均 106.3 → B 均 127.0，差 +20.7 字，95% CI [+0.6, +40.7]。

**判断错误（已改口）**：这一条曾被当成「RAG 没用」的证据。**不对。** 赛题的
「记忆融合」有两半——①**从本人历史抽事实**（`rag/memory.py`，两臂都开着，**根本没被测过**）；
② 跨对话检索同主题回复（本次 A/B 测的就是这一半）。A/B 只否定了后半。
失败的机制是：BM25 召回的是「同主题」而非「同一个人的长期记忆」，而融合层把它渲染成
「这个用户的历史」，模型看到别人的经历反而干扰情绪判断。

**已做的修法**：检索块从 user 段末尾移到 **system**（`PARTICIPANT_RETRIEVED_IN_SYSTEM`，
commit `9c2f301`），避免被当成「用户又说了这些」。**效果未验证。**

## 四、负结果（试过但没采用的方案）

> 这一节是加分项：把死路记下来，专家评审能看到我们真的做了实验设计。

1. **「目标回复前 30 字出现在历史里」作为泄漏判据** —— 误报 41 条。
   情感陪伴场景里 `嗯，我在听。`/`死心。` 这类 2~4 字口头回应**本就高频重复**，
   重合率天然 100%。最终判据改成双门槛：短重复要求
   `len ≤ 40 且长度差 ≤ 8`，真泄漏要求 `len ≥ 60 且重合率 ≥ 0.60`，
   结果从 41 条收敛到 **2 条真泄漏**（`train_002907_t15`、`train_005955_t15`）。
2. **「训练集记忆编号能被模型学会」** —— 不成立。train 与 val 的 memory id
   **零重叠**（26,883 vs 3,301），靠记住编号预测 `memory_refs` 在验证集上必然为 0。
3. **全量跑 O(n·m) 最长公共子串** —— 18,653 条上超过 120 秒。
   改为先过两道廉价门控（字符集合交集比例、长度倍数），再跑 DP。
